★ Flagship — ADO • Azure DevOps06

ADO Release Delivery & Defect Reporting — 600 Devs + 250 Testers

Are we ready to ship the next release? This report answers it every day for RTEs, clients and stakeholders: how delivery is tracking to the release date, how many defects we've fixed, and how many new bugs we're creating on the way there. If bugs created outrun bugs fixed, the release isn't getting healthier — this dashboard makes that impossible to miss.

850Team — 600 devs + 250 testers
Created vs FixedDefects — the core release signal
3 audiencesRTE • Client • Stakeholders

Sample view: the story is the crossover — fix rate overtaking creation rate, and the open-defect backlog burning down to the release.

What each audience gets
  • RTE support — Release readiness, feature & story completion by team / PI, blockers and risks to the release train.
  • Client reporting — A clean, non-technical view: are we on track, what's delivered, what quality looks like.
  • Stakeholder reporting — Defect burndown, severity mix, created vs fixed trend, and go / no-go signals for the release.
What's inside the report
  • Release readiness — % features / stories done vs planned for the target release.
  • Defect flow — Bugs created, defects fixed, net change & open backlog by severity and team.
  • Quality trend — Sprint-by-sprint created vs fixed, so a bad sprint shows up immediately, not at release time.

Flagship deep dive

From R Shiny + Jenkins to Power BI + ADO — one reporting pipeline, two generations

This wasn't a one-off dashboard. It was a reporting pipeline serving a large product organisation — 600 developers and 250 testers — through the whole run-up to a release. The questions never changed; the platform did.

1 · R Shiny web appOriginal build: interactive release & defect reporting as a Shiny web app, so RTEs and stakeholders could self-serve instead of asking for exports.
2 · Jenkins + CI/CDAutomated pipeline to refresh, test and publish the reporting — no manual rebuild before every stakeholder meeting.
3 · Move to ADOTeam migrated work tracking to Azure DevOps. Source of truth became ADO work items: features, stories, tasks, bugs & defects.
4 · Rebuilt in Power BISame measures, rebuilt on ADO data in Power BI: release readiness, defect created vs fixed, burndown and stakeholder views.
ADO Work ItemsFeatures, stories, bugs, defects, test outcomes from ADO boards / queries
Clean & ModelWork-item history flattened, iterations & area paths as dimensions, star schema
DAX MeasuresCreated, Fixed, Open, Net Change, Fix Ratio, % Complete — by release & sprint
RTE ViewTrain-level readiness, risks, blockers, team-by-team delivery
Client ViewStakeholder summary: on track? quality? go / no-go for release?

How to talk about it in an interview: “Ask me about the crossover point. Early in a release, created > fixed is normal. The report earns its keep when it shows — by severity and by team — exactly when fixed starts beating created, and whether the remaining open defects are actually release-blocking or not.” Sample data is used in this portfolio recreation; scale, audiences and workflow are from my real work.

# Python — pandas: cleaning a messy sales export
import pandas as pd
df = pd.read_csv("sales_raw.csv")
df["order_date"] = pd.to_datetime(
    df["order_date"], dayfirst=True, errors="coerce")
df = df.drop_duplicates(subset=["order_id"])
df["region"] = (df["region"].str.strip()
                 .str.title())
df["revenue"] = df["revenue"].fillna(0)
df.to_csv("sales_clean.csv", index=False)
# R — dplyr + janitor: the same job, tidyverse way
library(dplyr); library(janitor)
sales_clean <- sales_raw %>%
  clean_names() %>%
  distinct(order_id, .keep_all = TRUE) %>%
  mutate(
    order_date = as.Date(order_date),
    region = tools::toTitleCase(trimws(region)),
    revenue = coalesce(revenue, 0)
  )

Why both Python and R? I use whichever fits the data and the team — the goal is a clean, trusted table that Power BI can model well, not loyalty to one tool.

How I build a report

The same process behind every project above — and behind my production work.

  1. 1
    Start with the decision

    What will someone do differently after seeing this? That question picks the KPIs.

  2. 2
    Wrangle honestly

    Python and R to fix duplicates, nulls, dates and categories — and document it.

  3. 3
    Model before visuals

    Clean star schema first. Good models make DAX simple and reports fast.

  4. 4
    Write measures, not calculated clutter

    Reusable DAX measures for every KPI, so numbers stay consistent everywhere.

  5. 5
    Design for scanning

    KPIs on top, trend in the middle, detail on drill-through. No chart junk.

DAX Lab

Real measures from these projects — tap Copy to reuse them.

Revenue YoY %

Revenue YoY % =
DIVIDE (
    [Total Revenue] - [Revenue LY],
    [Revenue LY]
)

Revenue Last Year

Revenue LY =
CALCULATE (
    [Total Revenue],
    SAMEPERIODLASTYEAR ( 'Date'[Date] )
)

Budget Variance %

Budget Variance % =
DIVIDE ( [Actual] - [Budget], [Budget] )

ADO — Net Defect Change

Net Defect Change =
[Bugs Created] - [Defects Fixed]
-- Negative = backlog is shrinking
-- Positive = creating faster than fixing

ADO — Defect Fix Ratio

Defect Fix Ratio =
DIVIDE ( [Defects Fixed], [Bugs Created] )
-- > 1.0 = fixing faster than creating
-- The release-readiness crossover signal

ADO — Bugs Created / Fixed

Bugs Created =
CALCULATE ( COUNTROWS ( 'Work Items' ),
  'Work Items'[Work Item Type] = "Bug" )

Defects Fixed =
CALCULATE ( COUNTROWS ( 'Work Items' ),
  'Work Items'[State] IN { "Closed", "Resolved" } )
